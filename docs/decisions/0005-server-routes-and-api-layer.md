# 0005. Server routes, the API layer, and how its acceptance tests are red on the base

- Status: proposed
- Date: 2026-11-23
- Deciders: milestone P2 worker; a human owner confirms by approving the PR

## Context

- Plan 6.2 marks the TanStack Start server-route API `[CHECK]`. Read from `@tanstack/start-client-core` 1.169
  (`dist/esm/serverRoute.d.ts`) and `@tanstack/start-server-core` (`dist/esm/createStartHandler.js`, `handleServerRoutes`):
  a server route is a file route with a `server` option, `createFileRoute("/api/v1/rooms")({ server: { handlers: { GET,
POST, ANY } } })`. Start matches the path with `router.getMatchedRoutes(pathname)`, requires an exact match, and calls
  `handlers[method] ?? handlers.ANY` with `{ request, params, pathname, context, next }`. There is no separate
  `createServerFileRoute` any more (older docs and blog posts show one). Route-level and global request middleware exist
  (`server.middleware`, `createStart({ requestMiddleware })`).
- The build output is `app/dist/server/server.js`, whose default export is `{ fetch(request) }` (no listener). The client
  bundle contains no server code (checked: no `drizzle`, `jose`, `createHmac` or `PUBLIC_ENDPOINTS` in `dist/client`).
- `prove-red` (F1) runs each new `@ac` test against the merge base and needs it to fail on an assertion. P2 starts the
  server from nothing, so no server module exists on the base, and a static import of one fails to load (wrong reason).

## Decision

- **No Start middleware for auth.** Every handler is created with `bind(contract, handler)` from
  `app/src/server/http/endpoint.ts` and handed to Start with `serve({...})`. The wrapper does correlation id, access
  (`user` by default; `public` only for entries on `PUBLIC_ENDPOINTS`; `sefaria-webhook` by signature), zod validation of
  input and output, error mapping and the single log line. `serve` adds an `ANY` handler that authenticates before
  answering 405. Reason: it is plain code we can test without the Start runtime, and the route-enumeration test proves
  from the outside that nothing bypasses it (a raw handler would answer without 401 and fail that test).
- **Contracts are the single source.** `app/src/server/api/contracts.ts` lists every endpoint; OpenAPI and the client are
  generated from it; a test checks that the served route tree and the contract list are the same set.
- **Postgres + Drizzle** (plan D3 default), SQL migrations generated by drizzle-kit and applied with Drizzle's migrator;
  `pg` (node-postgres) as the driver.
- **Acceptance tests reach the API through the served route tree** (`getRouter()` then `getMatchedRoutes`), exactly as
  Start dispatches, and live directly in `app/src` (entry level, which the layer rule lets import the route tree). Each test
  first asserts its entry point exists (the route is served, or `import.meta.glob` finds the module), then loads the shared
  harness with a dynamic import. On the base the first assertion fails (an `AssertionError`), which is the honest reason:
  the feature is not there. The CI `integration` job also runs the real built server's `fetch` handler (`npm run
smoke:server`).

## Consequences

- The "entry point exists" assertion is weaker than testing through an existing module, which the F1 rule prefers; for a
  greenfield server there is no such module. The owner should confirm this pattern or tighten `prove-red`.
- Start middleware stays available for later cross-cutting needs (for example CORS for the surface origin); auth must stay
  in the wrapper so the enumeration test keeps covering it.
- `vitest run` without `--project` now includes the `integration` project and needs Postgres (`TEST_DATABASE_URL`).
